# Threat model

## What are we building?

A multi-tenant job service. Tenants submit documents, jobs run and commit results, and every step is recorded in a per-job hash chain that can be replayed. One tenant must never read or change another tenant's data, and must not be able to tell whether another tenant's data exists.

**Assets**
- Tenant rows in `documents`, `document_versions`, `jobs`, `attempts`, `artifacts`, `outbox`, `processed_events`, `audit_events`, `cap_grants`, `job_checkpoints`, `extractions`, `extracted_facts`, `extraction_dead_letters`, `extraction_revocations` and `extraction_budgets`.
- Per-tenant content bytes at `tenants/{tenant}/{sha}`.
- Capability grants, which authorize every commit.
- Each job's audit chain and checkpoints, and exported copies of a chain (`anvil-chain/1` files), which hold a job's hashes, payloads and tenant ID outside the database (record 0026).
- The model credential (`ANVIL_MODEL_API_KEY`), which spends the operator's model allowance, and each tenant's call budget and the kill-switch, which limit that spending (record 0023). It is also a GitHub repository secret for the nightly live eval (record 0024).

**Trust boundaries** (marked in `docs/architecture/containers.mmd`)
1. **HTTP entry.** Tenant clients send untrusted requests and documents.
2. **Database.** Tenant queries run under row-level security as the runtime role `anvil_app`, which is `NOBYPASSRLS` (row 'Cross-tenant rows' below). The Compose default login, `anvil`, bypasses row-level security, so a deployment that runs on it has no RLS on its queries. The operator CLI (`anvil replay`, `anvil export`) connects here directly, without the API, in a read-only session; it switches a login that bypasses row-level security to the runtime role first, and refuses to read if it can't (record 0026).
3. **Exec jail.** Tenant-supplied commands run here, inside a bubblewrap sandbox. No production code calls it yet.
4. **Network egress** through the parent's `JailEgress` broker. The jailed child has no network of its own.
5. **Content store.** Files on disk, reached through presigned URLs.
6. **Model provider.** Extraction sends the first 500 characters of a tenant's document to the DeepSeek chat completions API over HTTPS, and treats the reply as untrusted input (record 0022). The nightly live eval sends the generated full-v1 set the same way, from GitHub Actions (record 0024).
7. **Exported chain files.** `anvil verify` reads a file that anyone holding it may have edited, so the file is untrusted input. It is checked with no database connection (record 0026).

## What can go wrong?

- **A forged or missing tenant identity** reads or writes another tenant's rows.
- **Connection-pool reuse or a cached plan** leaks rows across tenants.
- **Cross-tenant IDs, search cursors or content hashes** reveal whether another tenant's data exists (an oracle).
- **A stale or zombie worker** commits after its lease moved on, or a revoked capability still commits.
- **A tenant floods the queue** and holds the worker pool, so other tenants' jobs wait behind it.
- **A database restore** rewinds fencing tokens and capability grants, so a worker from the lost timeline holds a token or grant that the restored database issues again.
- **Path traversal or symlinks** in content paths or workspace files escape the tenant's directory.
- **A presigned URL** is swapped to another tenant, tampered with, replayed after expiry, or used after its capability is revoked.
- **Audit chain tampering:** an event is edited, deleted, forked or dropped, and replay reports a false match.
- **The operator CLI** reads another tenant's chain or reveals that it exists, writes to the database, or reads with row-level security bypassed.
- **An exported chain** is edited (an event, a checkpoint, or the unhashed header naming the job's state and input), so the offline verifier reports a false match or the wrong place; or a hostile file exhausts it.
- **Jailed code** reads a sibling workspace, inherits secrets through environment variables, floods output, or reaches the network (metadata endpoints, internal addresses, redirects).
- **Unbounded input:** oversized titles, bodies or keys.
- **Model output:** a citation invented or paraphrased, a value the cited text doesn't hold, an instruction hidden in a document steers what is emitted, malformed output gets indexed, or a new prompt or model is quietly worse.
- **Extraction across tenants:** a forged or other tenant's document ID is extracted or reveals that the document exists, or a shared result, cache or dedup key lets one tenant's extraction answer another's.
- **Poison input:** binary, empty, control-character or hidden-character content, a missing or corrupt stored body, or a document built to make the model refuse or emit junk, gets indexed, blocks the tenant, or fails the request instead of being quarantined.
- **Tenant text leaves the system:** the provider keeps or trains on what it's sent, or the credential leaks.
- **Model spend runs away:** a tenant, a retry loop or several processes make unbounded paid calls, the runtime tops up its own budget, or calls can't be stopped during an incident.
- **The extraction cache misleads:** a hit crosses tenants, or a quarantined, tampered or revoked result is served or reused.
- **The eval set is edited or tuned on,** so the gate stops measuring.
- **The nightly live eval** exposes the model key to a pull request or to steps that don't need it, or fails quietly so a drifting model goes unnoticed.
- **The full-text index** slows every fact insert, stalls one on a pending-list merge, or grows without bound, and can't be removed during an incident.
- **A secret is committed,** or a dependency or CI action is compromised.

## Did we do enough?

Not fully. These risks are accepted for now:

- **The jail has no syscall filter or resource limits** (record 0019). A kernel exploit from inside the sandbox, a fork bomb or memory exhaustion isn't contained. The host must allow unprivileged user namespaces. In a container, that means relaxed seccomp and AppArmor profiles and unmasked `/proc` paths, which the production image doesn't have yet. The tenant lock is per JVM.
- **The leak matrix leaves out sweeps.** `RlsLeakTest` interleaves two tenants on one pool across all 13 tenant-scoped tables and the submit, claim, fair claim (`claimNext`), heartbeat, commit, capability, relay, read, search, audit read, replay and CAS paths (#74). Reconcile and garbage collection sweep every tenant by design and aren't in the matrix. `claimNext` sweeps every tenant too, but the matrix runs it as the restricted role.
- **Fair claim limits** (record 0020). The default quota (1000) caps nothing until an operator sets one, so without it fairness comes only from the penalty. The quota counts jobs, not their cost. Under many workers the order is best-effort (one ranking snapshot, the penalty isn't re-read at claim time); the quota is exact. `claimNext` time grows with the number of tenants, and one tenant's claims serialize on its lock.
- **Eval gate limits** (record 0021). With 40 documents, a candidate worse on 3 documents and better on none passes; one worse on 4 or more fails. A candidate better on some documents and worse on others can lose F1 and still pass. The attack check compares counts with a baseline fooled in 3 of 12 cases, so it allows up to 3. The set is short English text with four fields, and its author knew the baseline's rules, so the baseline's score is biased low. The never-tuned-on rule is mostly procedural: the 8-word check can't see paraphrased examples or rules derived from the set.
- **Full-set limits** (record 0024). The full set is generated from templates, so its text is more regular than real documents, and the model scores higher on it than on the hand-written pilot. Its injection suite has five cases per language other than English, too few to bound any one language. The nightly run's verdict depends on the provider: a model changed behind the same name, an outage or a missing key all fail it.
- **Extraction limits** (record 0022). The harness run in record 0022 had 0 of 12 injection cases succeed (rate 0.000, interval up to 0.242), and the full-set run in record 0024 had 0 of 72 (interval up to 0.051); the prompt and checks can't stop a planted value that is also a plausible fact, written in the document and cited exactly. Requests go to a third party: DeepSeek's API documentation doesn't say how long inputs are kept or whether they train models, so its terms and privacy policy must be checked before tenant traffic is sent; the harness sends only fictional documents. The tenant cache, call budget and kill-switch are in record 0023, which restricts extraction to tenants an operator grants a budget. Fallback results are the baseline's quality, which lets 3 of 12 attacks through. A call admitted just before the kill-switch flips still runs. The model call holds the HTTP request for up to 60 seconds per attempt with 2 retries, and concurrent requests in different processes can each spend a call on the same version. A version quarantined for a one-off malformed reply stays quarantined under its prompt and model, though another version with the same text is asked again. A revoked version is answered by the rules until it is resubmitted. That a forged and an existing other-tenant ID look the same is proven for status and body, not for timing.
- **Load limits** (#79, `load/README.md`). One process completes at most about 170 extractions a second on the measured host, because each model call holds a request thread. There is no admission control: a flood queues instead of being refused, and with a deep queue throughput falls below 140 a second. The runs use a stub with the model's recorded latency, on one host with default settings. No soak numbers are claimed, because the full-text index is over budget (record 0025). The provider's behaviour under load, a real 24-hour soak and autoscaling aren't measured.
- **Replay cost grows with chain length** (#76). Replay re-verifies the whole chain, so a long chain makes it slow (chain DoS). The offline verifier does the same, and reads exports of at most 8 MiB (record 0026).
- **No key signs a chain** (record 0026). Anyone who can write an export, or the audit tables, can rewrite a chain whole with every hash recomputed, and it still verifies. The verifier prints `head`, the last event's hash, so it can be compared with a value kept elsewhere; nothing anchors heads outside the database yet. An export is tenant data at rest: whoever holds the file can read the chain's payloads, and keeping it safe is the operator's job.
- **Parts of an export that no hash covers** (record 0026). A relabelled export, with every `tenant_id` changed, verifies as the new tenant with the same `head`, so the operator must know which tenant a file came from. The checkpoints aren't hashed, so removing one removes its check, and a tail rewritten with every hash recomputed passes once the checkpoints past the edit are gone. The events after a job's terminal commit can be cut without changing the verdict, only `head` (and `output_sha` when a `cas.put` is cut). A checkpoint that names no event of the chain, which a cut tail leaves behind, is refused.
- **The CLI trusts its database login.** It refuses a role that can't become `anvil_app`, or that still bypasses row-level security after switching; anyone with database credentials can read every tenant's rows with `psql` anyway.
- **Some restores aren't detected** (#34, record 0016). A storage snapshot rolled back in place, or a base backup started without `recovery.signal`, keeps the timeline, so the gate stays open. Effects outside the database from after the restore target can repeat, and the old primary must be gone before the restored one serves.
- **A time-of-check gap after each grant check.** A revoke that lands after a commit's grant check takes effect from the next commit.
- **Some steps aren't logged:** heartbeat, reclaim, empty polls and `outbox.sent_at`. Replay's output is the same without them.
